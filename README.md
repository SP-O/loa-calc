# 로아도쓰 (LoaDoss)

로스트아크 플레이어를 위한 계산기 세 개를 운영하는 개인 웹사이트입니다.
경매장 시세를 실시간으로 받아 제작 손익을 계산하고, 전리품 경매의 적정 입찰가를 구하고,
미니게임 티카투카의 최적 수를 추천합니다.

**https://loadoss.com**

2026년 3월부터 혼자 만들고 운영 중입니다.

---

## 도구

### 아비도스 융화 재료 제작 계산기 — [`/`](https://loadoss.com/)

생활 재료로 아비도스 융화 재료를 만들 때의 손익을 계산합니다.

- **재료 교환 계산** — 보유 재료로 만들 수 있는 최대 횟수와 그때의 교환 경로. 기본/영지 농장 두 모드
- **목표 제작 계산** — 원하는 제작 횟수에 필요한 재료를 역산
- **제작 수익** — 실시간 시세 기반 손익. 판매 수수료 5%, 영지 제작 수수료, 대성공 확률 반영
- **제작 랭킹** — 벌목·채광·고고학·낚시·수렵·채집 여섯 생활의 손익 순위
- **시세 차트** — 재료별 14일 평균 거래가·거래량

### 경매 입찰 계산기 — [`/auction`](https://loadoss.com/auction)

레이드 전리품 경매에서 얼마까지 입찰해야 이득인지 계산합니다.
손익 분기점 · 추천 입찰가 · 최대 이득가 · 싸게 노리기 네 가지 값을 제시하고,
각 금액에서 상회 입찰당했을 때 분배금이 어떻게 달라지는지 함께 보여줍니다.

입력한 금액과 시세가 비슷한 아이템의 14일 거래 차트를 자동으로 띄웁니다.
경매 보상으로 나오는 유물 각인서 전 종류와 영웅 등급 젬을 지원합니다.

### 티파고 — 티카투카 계산기 — [`/tikatuka`](https://loadoss.com/tikatuka)

로스트아크의 주사위 미니게임 티카투카에서 이길 확률이 가장 높은 수를 추천합니다.

- **완전탐색 + 몬테카를로** — 남은 경우의 수가 적으면 완전탐색, 많으면 롤아웃
- **화면 인식** — 게임 화면을 공유하면 보드와 굴린 주사위를 자동으로 읽습니다
- **오버레이** — Document Picture-in-Picture로 게임 위에 추천을 띄웁니다
- **리롤 판단** — 지금 굴린 주사위를 쓸지 다시 굴릴지 승률로 비교

## 기술 스택

| 구분 | 사용 기술 |
|---|---|
| 프론트엔드 | Vue 3 (전역 빌드), Chart.js, 순수 ES 모듈 |
| 티파고 엔진 | Web Worker 3종 (완전탐색 · 몬테카를로 풀 · 화면 인식) |
| 화면 인식 | `getDisplayMedia`, Canvas, 템플릿 매칭 |
| 오버레이 | Document Picture-in-Picture API |
| 서버 | Vercel Serverless Functions (운영) · Cloudflare Pages Functions (이전 준비 완료) |
| 데이터 | 로스트아크 Open API |
| 그 외 | Firebase Realtime Database · Matter.js (이스터에그), GTM / GA4 |
| 테스트 | Node.js 내장 테스트 러너 |

**빌드 도구가 없습니다.** 번들러도 트랜스파일러도 쓰지 않고 정적 HTML과 전역 스크립트로
동작합니다. 페이지 13개 규모에서 빌드 단계를 들이는 비용이 이득보다 크다고 봤습니다.
Vue는 CDN이 아니라 저장소에 프로덕션 빌드를 두고 씁니다.

## 구현 이야기

만들면서 실제로 막혔던 문제들입니다. 전부 재현·측정으로 원인을 확정하고 고쳤습니다.

### 1. 솔버가 이길 수를 저평가하던 버그

사용자가 "6을 라인1에 두라는 추천이 이상하다"고 제보했습니다. 엔진은 87% / 62% / 59%로
라인1을 압도적 1등으로 뽑고 있었습니다.

원인은 게임 종료 판정이었습니다. 롤아웃과 탐색이 **둘 곳이 없는 플레이어의 차례가 되면
게임 전체를 끝내 버렸습니다.** 내 빈칸이 남아 있어도 상대가 먼저 꽉 차면 거기서 끝났습니다.
그래서 "나중에 라인1을 싸구려로 잠그는" 미래 배치가 통째로 사라지고, 전개형 수가 저평가됐습니다.

결정적 증거는 완전탐색에서 나왔습니다. **수학적으로 100%인 국면이 73.9%로 나왔습니다.**
노이즈가 없는 경로라 정책 문제임이 확정됐습니다.

수정은 간단했습니다 — 둘 곳이 없으면 게임을 끝내지 말고 턴만 넘깁니다.
결과는 87/62/59 → **95/93/90**. 30%p 격차가 가짜였고, 실제로는 어디 둬도 90% 이상
이기는 판이었습니다. 회귀 테스트 두 개를 남겼습니다.

이 수정으로 롤아웃이 끝까지 진행되며 느려진 부분(1,019ms)은 밑장 계산 최적화로
**425ms까지 되돌렸습니다.**

### 2. 완전탐색 40초를 1.9초로

빈칸이 3개뿐인 엔드게임인데도 완전탐색이 노드 한도를 넘겨 몬테카를로로 폴백하고 있었습니다.
알까기 재개방·보너스·밑장 분기가 곱해지면서 **2,800만 노드, 40초**가 걸렸습니다.

라인은 순서가 무관한 멀티셋이라는 점을 이용해 트랜스포지션 테이블을 넣었습니다.
상태를 13진수로 팩해 2단 Map으로 캐시하고, 자식 상태는 복사 대신 구조를 공유합니다.
**4.7만 전개, 1.9초**가 됐습니다.

같은 작업에서 평가함수의 잠금 규칙도 고쳤습니다. 양쪽이 꽉 찬 라인은 이미 승부가 확정된
자리인데 시그모이드로 애매하게 평가하고 있었습니다. 확정값으로 바꾼 뒤
**4만 판 아레나에서 신 59.35% vs 구 40.65%** 로 개선됐습니다.

### 3. 주사위 5를 3으로 읽던 화면 인식 — 오진 세 번

"1920 창모드에서 굴린 주사위 5가 3으로 깜빡인다"는 제보였습니다. 원인을 세 번 틀렸습니다.

**첫 번째 진단** — 3과 5는 대각선·중앙 점을 공유해서 템플릿이 가장 가깝습니다. 픽스처를
축소해 측정하니 5-vs-3 마진이 21%에서 6.4%로 붕괴했습니다. 두 템플릿이 가장 다른 픽셀만
골라 재비교하는 판별기를 넣어 마진을 24%로 올렸습니다. **배포했는데 제보가 계속됐습니다.**

**두 번째 진단** — 축소 시뮬레이션이 네이티브 렌더를 대체하지 못한다는 걸 그때 알았습니다.
사용자에게 실제 1920 캡처를 받아 다시 쟀더니 진짜 원인이 나왔습니다. 분류 창 크기를
캘리브레이션 값에서 뽑고 있었는데, 창모드에서는 그 값이 실제 주사위면보다 커집니다.
창이 커지면 **5의 모서리 점이 창 안에서 어긋나 3으로 매칭**됩니다. 5만 그런 이유는
5의 판별 점이 모서리에 있어 스케일 오차에 가장 취약하기 때문입니다.
분류 창을 캘리브레이션이 아니라 **실측 블롭 크기**에서 뽑도록 고쳤습니다.

**세 번째 진단** — 그래도 3초에 한 번씩 깜빡였습니다. 다시 측정하니 크기가 아니라
**중심 지터**였습니다. 정중심에서는 5가 압도적인데 4픽셀만 어긋나도 오분류됐고,
±4px 범위에서 25회 중 8회 실패했습니다. ±3px 이웃에서 최적 중심을 찾아 분류하도록
바꿔 **0/25** 가 됐습니다.

교훈은 하나입니다 — **화면 인식 버그는 사용자의 실제 해상도 캡처 없이는 재현되지 않습니다.**

### 4. 다른 계산기 일곱 곳이 공유하던 입찰가 수식 오류

"로스트아크 경매 계산기"로 검색해 나오는 계산기들에 같은 조건을 넣으면 **1골드도 다르지 않은
같은 값**이 나옵니다. 같은 식을 쓰고 있다는 뜻입니다.

그 식에는 오류가 둘 있었습니다.

첫째, **상회 입찰하는 사람의 대안을 0으로 봤습니다.** 실제 대안은 0이 아니라
"상회 입찰하지 않으면 현재가 기준 분배금을 받는다"입니다. 이걸 반영하면 분모가
`1.1N` 이 아니라 `1.1(N−1)+0.95` 가 됩니다.

둘째, 2025년 7월 23일 패치로 낙찰 수수료가 "10만 골드 초과분"에서 "낙찰 금액 전체"로
바뀌었는데 반영돼 있지 않았습니다.

10만 골드·8인 기준으로 검산하면, 기존 계산기가 "선점"이라 부르던 75,568골드에서 상대는
**상회 입찰하면 11,875골드, 안 하면 10,795골드**를 받습니다. 무조건 덮입니다.
"경매는 결국 분기점 직전까지 간다"는 유저들의 경험담이 이 오류의 증거였습니다.
수정한 값 76,879골드에서는 덮으면 10,433, 안 덮으면 10,434로 실제로 멈춥니다.

**소수점 처리는 인게임 실측으로 확정했습니다.** 8인·낙찰 112,596골드에서 분배금이
15,280골드였는데, 이 값은 수수료를 올림하고 분배금을 내림해야만 나옵니다.
수수료를 내림하면 15,281이 되어 어떤 반올림으로도 실측과 맞지 않습니다.

### 5. 트래픽이 몰리자 시세가 안 뜨던 문제

신기능 배포 후 접속이 늘자 재료 시세가 비었습니다.

서버리스 함수의 캐시가 **인스턴스별 메모리 변수**였던 게 원인입니다. 트래픽이 늘면
인스턴스가 늘고, 새 인스턴스마다 빈 캐시로 로스트아크 API를 44회(22종 × 시세·통계) 호출합니다.
분당 100회 제한을 넘겨 429가 돌아왔습니다. 여기에 클라이언트 타이머가 5분 정각에 맞춰져
있어 전 사용자가 동시에 요청했습니다.

세 겹으로 막았습니다.

1. **엣지 캐시** — 응답에 남은 블록 시간만큼 `s-maxage` 를 실어, 사용자 수와 무관하게
   함수 실행이 5분에 한 번
2. **인플라이트 공유** — 같은 인스턴스의 동시 요청은 진행 중인 갱신 하나를 함께 기다림
3. **강제 갱신 가드** — 새로고침 버튼은 직전 갱신 60초 이내면 캐시를 반환

클라이언트 타이머에는 0~30초 무작위 지터를 넣어 동시 폭주를 흩었습니다.

### 6. 계산기가 iframe 안에 있어 문서에는 없던 문제

`/auction` 과 `/tikatuka` 는 헤더·푸터만 있는 껍데기였고 계산기는 iframe 안에 있었습니다.
**iframe 내용은 부모 문서의 본문에 포함되지 않습니다.** 자바스크립트를 전부 실행한 뒤에도
`/auction` 의 본문은 223자였습니다 — 제목 한 줄과 설명 한 문장이 전부였습니다.

원래 iframe을 쓴 이유는 있었습니다. 티파고를 메인 페이지에 얹으려면 전역 CSS
(`button { width: 100% }` 같은 것)가 도구 버튼을 전부 깨뜨렸습니다. 격리가 필요했습니다.
그런데 도구가 독립 페이지로 분리되면서 그 전제가 사라졌고, iframe만 관성으로 남았습니다.

결정 전에 **동종 사이트 24곳(로스트아크 16 · 타 게임 8)을 전수 조사**했습니다.
콘텐츠 iframe을 쓰는 곳은 0곳이었습니다. 프레임워크는 제각각이었지만
"도구마다 고유 URL, 그 문서 안에 헤더+도구+푸터"라는 규칙은 같았습니다.

계산기 마크업을 페이지 문서로 옮기고 `/tools/*` 는 301로 넘겼습니다.
`/auction` 223자 → 1,584자, `/tikatuka` 217자 → 547자.
자바스크립트를 실행하지 않아도 계산기 라벨이 보이게 됐습니다.

옮기는 과정에서 함정이 하나 있었습니다. 도구가 테마를 `?theme=` 쿼리로 받고 있었는데,
정식 주소에는 그 값이 없어 라이트 모드를 도로 꺼 버렸습니다. 테마의 주인을 페이지 쪽으로
넘기고, 도구는 `body` 클래스를 관찰해 차트만 다시 그리도록 바꿨습니다.

## 로컬 실행

```bash
python dev_server.py
```

`http://localhost:8000` 에서 뜹니다. 로스트아크 Open API 프록시가 포함된 개발 서버라
API 키가 필요합니다. `dev_server.py` 는 로컬 전용이며 저장소에 포함되지 않습니다.

테스트는 Node.js 내장 러너를 씁니다.

```bash
node --test test/*.mjs
```

티파고 솔버와 화면 인식은 별도 개발 저장소에서 TDD로 만들었고, 회귀 테스트 140여 개가
그쪽에 있습니다. 이 저장소에는 실행 코드만 들어 있습니다.
